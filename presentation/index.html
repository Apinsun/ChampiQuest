Objectifs & périmètre

  • Prédire quand & où un champignon va fructifier (météo → probabilité de pousse).
  • Reconnaître l'espèce à partir d'une photo — en privilégiant la sécurité du cueilleur.
  • Rendre les modèles utilisables : API, carte interactive, page de démo.

3 semaines

  • Semaine 1 — partie 1 : prédiction météo → pousse (8 espèces, LightGBM).
  • Semaine 2 — partie 2 : reconnaissance d'espèce par image (20 classes, ConvNeXt).
  • Semaine 3 — FastAPI, carte journalière, Docker + CI/CD, préparation soutenance.

Le problème des absences

Les données GBIF ne contiennent que des présences : « champignon vu ». Pour apprendre « quand il ne pousse pas », il faut fabriquer des négatifs honnêtes.

  • Effort prouvé : un autre champignon a été vu au même endroit, le même jour, sans notre cible → c'est un vrai négatif (on a regardé, pas trouvé).
  • Buffer ±3 jours : un carpophore persiste plusieurs jours → pas de fausse absence autour d'une présence.
  • Fenêtre de fructification : les absences sont tirées dans la saison de l'espèce (morille : mars–mai, jamais en septembre).

→ chaque négatif encode « présence d'effort + absence de l'espèce », pas « personne n'est sorti ».

Feature engineering (partie 1)

  • Fenêtres météo : pluie J7/J30/J90, bilan hydrique (pluie − évapotranspiration), choc/tendance thermique, température du sol.
  • Proxies de co-fructification : des espèces très corrélées à la cible sont ajoutées comme présences à l'entraînement (combat le manque de données, sans fuite : la localisation n'est jamais une feature).
  • Élagage data-driven : corrélations + SHAP → 13 features retenues (redondances et features mortes éliminées).
  • day_of_year : phénologie intra-saison (début vs plein vs fin de saison) — +0.05 AUC.
La localisation sert à récupérer l'environnement, jamais en feature → le modèle généralise (n'apprend pas les spots par cœur).

Modélisation (partie 1)

  • Un LightGBM par espèce (config simple : 50 arbres, 7 feuilles, profondeur 4).
  • Baseline : régression logistique (pour montrer l'apport du gradient boosting).
  • Évaluation : LOOCV par année — on entraîne sur toutes les années sauf une, on prédit l'année retirée ; répété pour chaque année (aucune fuite temporelle).
  • Proxies exclus du test (ils ne servent qu'à l'entraînement, sinon ils gonflent l'AUC).

Lexique express

AUC : aire sous la courbe ROC — on balaye tous les seuils, on trace vrais positifs vs faux positifs, on intègre l'aire. Concrètement : la probabilité qu'un jour « pousse » tiré au hasard soit mieux classé qu'un jour « ne pousse pas ». 0,5 = hasard · 1 = parfait.

LOOCV : leave-one-out par année — on entraîne sur toutes les années sauf une, on prédit l'année retirée, répété pour chaque année. Aucune fuite temporelle.

L'AUC par espèce évite qu'une espèce facile gonfle une moyenne globale. La LOOCV par année écarte toute fuite temporelle (le jour J et J+1 sont très corrélés). Le spread 0,72–0,89 reflète la difficulté du signal : girolle et cèpe sont plus diffus, trompette et lépiote plus nettement saisonnées.

Ablation : 1 modèle vs N modèles

Leçon

  • Mutualiser les espèces dilue la capacité du modèle.
  • L'AUC par espèce (slicée) est la comparaison honnête — l'AUC globale serait gonflée par la feature espèce.

Sécurité des cueilleurs

Toutes les erreurs ne se valent pas : annoncer « comestible » un champignon toxique est bien plus grave que l'inverse.

Calibration

  • Temperature scaling post-entraînement → probabilités fiables (pas juste un argmax).

Décision à coût

  • Comestible prédit sur toxique : ×10
  • Comestible sur « étranger » : ×8
  • Abstention si confiance < 0.6 → « je ne sais pas ».
0 erreur dangereuse

après calibration + décision à coût.

L'argmax seul en commettait 2,8 % (comestible prédit toxique) — la matrice de coût les élimine.

Lexique

Temperature scaling : on divise les logits par une température apprise → vraies probabilités (l'argmax ne change pas).

Matrice de coût : on choisit la classe qui minimise le coût attendu, pas la plus probable.

Insister : la dangerosité n'est PAS mise dans la loss (on garde une loss propre), elle est appliquée en post-traitement via la matrice de coût + l'abstention. Détails dans reports/ajout-especes-calibration.md.

Explicabilité vision (Grad-CAM)

Grad-CAM : où le modèle regarde pour décider (réel | heatmap).
Courbes d'entraînement (loss / F1).
  • Le modèle se focalise sur le champignon (chapeau, lames), pas sur le fond.
  • Même sur les sosies, la zone d'intérêt est discriminante → on peut faire confiance à la décision.
Grad-CAM : on propage le gradient de la classe prédite jusqu'à la dernière couche convolutive. Chaque canal de la feature map est pondéré par la moyenne de son gradient (= son « importance » pour la décision), puis on somme les canaux → heatmap des pixels qui activent la prédiction, superposée à l'image (colormap « jet »). Garde-fou : si la zone chaude est sur le fond plutôt que sur le champignon, le modèle se trompe de signal. Code : src/champiquest/vision/explain.py.

La précision GBIF, plafond du projet

Coordonnées souvent floutées à ~1 km → impossible de relier une observation à « l'arbre sous lequel elle a poussé ».

Dans le classifieur

  • Features habitat (type de forêt) : +0,002 d'AUC (ablation) → mortes.
  • Les pseudo-absences partagent le même habitat que les présences → la feature ne discrimine pas.

Même avec un SDM dédié (testé)

  • BD Forêt V2 (0,5 ha) + présence vs background → AUC 0,47–0,57 ≈ hasard.
  • 86 à 98 % des points tombent hors du bon polygone forestier.
SDM — Species Distribution Modeling

Prédit où une espèce vit à partir des conditions environnementales de ses observations. Presence-only : pas besoin d'absences — on compare les présences à des points de fond du paysage.

→ Le signal d'habitat fin est irrésolvable avec cette précision GPS. Le masque CLC (robuste au bruit) reste le bon compromis.

On a testé l'idée la plus naturelle : un SDM presence-only sur la donnée forestière la plus fine (BD Forêt V2, 0,5 ha). Résultat : AUC ≈ 0,5, car les coordonnées GBIF (~1 km) ne tombent presque jamais dans le bon polygone (86–98 % hors forêt). La limite est la donnée, pas la modélisation — c'est mesuré, pas supposé.

Limites & perspectives

  • Précision GBIF (~1 km) = plafond réel : même un SDM dédié échoue (AUC ≈ 0,5, testé — slide précédente).
  • Airflow pour orchestrer le refresh météo + la carte chaque jour (DAG, retries, monitoring) — plutôt qu'un simple cron.
  • Étendre la vision à plus d'espèces (le pipeline d'ajout est documenté et générique).

Anti-sur-ingénierie assumée : périmètre MVP, chaque ajout testé par ablation.

La précision GBIF (~1 km) est le plafond réel, mesuré (SDM BD Forêt V2 → AUC ≈ 0,5). Perspectives restantes : l'orchestration Airflow du pipeline quotidien et l'extension de la vision à plus d'espèces.

Conclusion

  • Partie 1 : 8 espèces, LightGBM un-par-espèce, AUC 0.811 (LOOCV), interprétable (SHAP).
  • Partie 2 : ConvNeXt 20 classes, 0 erreur dangereuse grâce à calibration + décision à coût.
  • Partie 3 : API + carte + démo, déployées via Docker & CI/CD.

Chaque choix est justifié par une baseline ou une ablation : régression logistique, élagage de features, modèle unique vs N, décision à coût.
